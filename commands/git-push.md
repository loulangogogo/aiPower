# /git-push 命令

## 触发方式

**仅在用户显式执行 `/git-push` 时运行。** 用户未显式调用时，即使上下文看起来「该提交并推送了」，也不得主动执行本命令。

命令调用即为本次提交与推送的授权；提交前仍需完成第 2 步的清单确认。

## 硬性禁令

任何情况下都不得执行：

- `git push --force` / `--force-with-lease` / `--force-if-includes`
- 带 `+` 前缀的 refspec（如 `git push origin +main`）
- `git add .` / `git add -A`——必须逐路径暂存用户确认的文件
- `git merge`、`git pull`（不带 `--rebase`）——本命令同步远程只用 rebase
- rebase 冲突后自行编辑冲突文件并 `git rebase --continue`，或使用 `--skip`
- 未完成第 2 步确认就执行 `git add` / `git commit`
- 删除远程分支或远程 tag

推送被中止时，唯一允许的动作是回滚并输出报告，然后结束。

## 执行流程

### 1. 变更检测

```bash
git status --porcelain
```

无输出 → 输出「当前分支无代码变更，无需提交。」并结束。

### 2. 确认要提交的文件

把 `git status --porcelain` 的每条结果整理成清单写在回复正文里，逐条给出 `<状态> <文件路径>`，状态翻译为：新增 / 修改 / 删除 / 未跟踪（将被新增）/ 重命名。

- **未跟踪文件必须单独标注**：临时脚本、密钥、构建产物最容易在这一步被误提交。
- 疑似敏感文件（`.env`、`*.pem`、`id_rsa`、`credentials*` 等）照常列出，但标注「⚠️ 疑似密钥」并排在最后。
- 附一行统计：`共 N 个文件，+X / −Y 行`（行数由 `git diff --stat HEAD` 汇总，不含未跟踪文件）。
- 不主动粘贴完整 diff；用户当场要求时再展示。

`AskUserQuestion` 每次只接受 **2–4 个选项**，所以**不要为每个文件生成一个选项**。用二选一发起确认：

- 问题文本：「以上 N 个文件是本次要提交的内容吗？」
- 选项：`[全部提交]` / `[取消]`

用户需要只提交其中一部分时，会通过该工具自带的 Other 输入路径。以用户给出的路径为准；若 Other 里提到清单之外的文件，先核实它确实有变更再纳入，否则忽略并说明。

分支处理：

- **全部提交** → 进入第 3 步。
- **取消**，或用户指出清单有误 → **整个命令中止**，不执行任何 `git add` / `git commit` / `git push`，输出「已取消，未提交任何文件。」并把控制权交回用户。
- **无人应答或交互不可用** → 中止（fail closed），**绝不默认全部提交，也绝不默认继续**。

未被确认的文件原样留在工作区，**绝不丢弃**，并在第 3 步结果中告知用户还剩多少未提交。

若 `AskUserQuestion` 工具不可用，或调用失败 → **不要退化成「自己决定并直接提交」**：改为在正文中完整列出候选文件及其状态，明确请求用户确认，等用户回复后再继续。

### 3. 提交

按 `/git-commit` 命令的规范生成中文提交信息，再按确认结果**逐路径**暂存（用 `--` 分隔并加引号，兼容空格、中文与特殊字符；重命名条目按新路径传入）：

```bash
git add -- "<路径1>" "<路径2>"
git commit -m "<message>"
```

输出「已提交 N 个文件，另有 M 个文件留在工作区未提交。」（N 为确认数，M 为未确认数）

先提交、后同步是必须的顺序：`pull --rebase` 要求工作区干净。若第 2 步只确认了一部分，提交后工作区可能仍有已跟踪文件的改动，第 6 步会据此判断。

### 4. 上游检查

```bash
git symbolic-ref --short -q HEAD        # 输出为空表示 detached HEAD，中止
git rev-parse --abbrev-ref '@{u}'       # 失败表示无可用上游，中止
```

任一检查失败 → 输出「当前分支未关联可用远程，请先执行 `git push -u <remote> <branch>` 建立关联。」并结束。

检查通过后动态取远程名与分支名，**后续步骤一律使用该值，禁止硬编码 `origin`**：

```bash
BRANCH=$(git symbolic-ref --short HEAD)
REMOTE=$(git config "branch.$BRANCH.remote")
```

### 5. 同步与比较

```bash
git fetch "$REMOTE"
git rev-list --count "HEAD..@{u}"    # behind：远程领先数
git rev-list --count "@{u}..HEAD"    # ahead ：本地领先数
```

### 6. 决策

**场景 A：`behind == 0`（远程未领先，可 fast-forward）**

```bash
git push
```

输出「推送成功！已将包含新提交的分支推送到 <远端分支名>。」

工作区是否残留未提交文件不影响 push，无需处理。

若 `git push` 被拒绝（non-fast-forward，说明同步间隙又有人推送）→ 进入场景 B 的中止流程，**不得改用 `--force`**。

**场景 B：`behind > 0`（远程有新提交）**

rebase 要求工作区没有已跟踪文件的改动，先检查：

```bash
git status --porcelain --untracked-files=no
```

- **有输出**（第 2 步只确认了一部分，仍有已跟踪文件未提交）→ **中止**，不执行 rebase，输出报告并提示：未提交的已跟踪文件会阻断 rebase，请先处理（提交或暂存）后重跑本命令。
- **无输出** → 执行自动 rebase 同步：

```bash
git pull --rebase "$REMOTE" "$BRANCH"
```

  - **成功** → 重新执行第 5 步比较：
    - `behind == 0` → 执行 `git push`，按场景 A 输出成功消息。
    - `behind > 0`（同步间隙又有人推送）→ 中止并输出报告，**不要循环重试**。
    - 未跟踪文件不阻断 rebase，会被原样保留；rebase 会重写本地未推送提交的哈希，这是预期行为。
  - **失败（冲突）** → 严格按此顺序处理：
    1. `git diff --name-only --diff-filter=U` 记录冲突文件（**必须在 abort 之前执行**，abort 后工作区不再保留冲突信息）
    2. `git rebase --abort` 回滚到 rebase 之前的状态
    3. 中止并输出报告

  **禁止**手工编辑冲突文件后继续 rebase，**禁止** `--skip`，**禁止**改用 merge。冲突一律交还用户。

## 中止报告模板

```text
⚠️  推送已中止：<中止原因>

📊 状态详情：
   - 当前分支：<BRANCH>
   - 远程分支：<REMOTE>/<BRANCH>
   - 本地领先远程：<ahead> 个提交
   - 远程领先本地：<behind> 个提交
   - 本次已提交：<N> 个文件
   - 仍留在工作区未提交：<M> 个文件
   - 自动同步结果：<未执行（工作区有未提交的已跟踪文件）/ 已 rebase 成功 / 冲突已回滚 / push 被拒绝>

📝 冲突文件（rebase 冲突时列出）：
   <git diff --name-only --diff-filter=U 的输出>

💡 建议操作：
   为防止覆盖远程上的他人提交，推送已阻止。本地提交完好无损。
   请选择处理方式：
   [1] 处理掉工作区未提交的已跟踪文件后重跑本命令（未提交的已跟踪文件会阻断 rebase）
   [2] 手动执行 git pull --rebase <REMOTE> <BRANCH> 并解决冲突后重跑本命令
   [3] 取消（手动处理）
```

报告中的选项仅供用户选择，**本命令不得代为执行**。

## 边界情况

| 情况 | 处理 |
| --- | --- |
| 工作区无变更 | 提示后结束，不推送 |
| 第 2 步取消确认 | 中止，不执行任何 git 写操作 |
| 第 2 步无人应答 / 交互不可用 | 中止（fail closed），绝不默认全部提交 |
| 只确认了部分文件，仍有已跟踪文件未提交，且 `behind > 0` | 中止，提示处理后重跑 |
| 仅剩未跟踪文件未提交，且 `behind > 0` | 照常 rebase（未跟踪文件不阻断），未跟踪文件原样保留 |
| 仍有未提交文件，但 `behind == 0` | 照常 push |
| detached HEAD | 中止并提示先切换分支 |
| 未关联上游 | 提示 `git push -u` 后结束 |
| 上游已配置但远程分支被删除（`@{u}` 解析失败） | 同上，按未关联上游处理 |
| rebase 冲突 | 先记录冲突文件 → `git rebase --abort` → 中止报告 |
| rebase 成功但推送前又落后 | 中止并报告，不循环重试 |
| `git push` 被拒绝（non-fast-forward） | 中止并报告，禁止改用 `--force` |
| 已有 rebase / merge 进行中 | 中止并提示先完成或中止当前操作 |

## 危险信号 — 出现即停止并输出报告

- 想用 `--force` / `--force-with-lease`「先把远程覆盖掉」
- 把「用户已执行 /git-push」当成可以跳过第 2 步确认的理由
- 图省事用 `git add .` 代替逐路径暂存确认的文件
- 把确认默认值改成「全部提交」，好让用户少点几下
- 用户还没确认就先 `git add` / `git commit`「省一轮来回」
- 为了清单好看而省略未跟踪文件或缩短列表
- 用 `--force` 之外的方式绕开「未提交的已跟踪文件阻断 rebase」，例如擅自 stash 或丢弃改动
- rebase 冲突后想自己解掉冲突再 `--continue`，把「让命令跑完」当成目标
- 反复 rebase 直到成功，无视一次次中断
- 觉得「用户很急，先推上去再说」
